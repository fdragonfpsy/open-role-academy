## Warum das wichtig ist

Ein Client, der nur im Normalfall funktioniert, scheitert in der Produktion: Das Netz ist langsam, ein Token läuft ab, der Server liefert einen Fehler, oder die Antwort ist auf viele Seiten verteilt. Robuster Integrationscode rechnet damit.

## REST-artige APIs

REST ist ein Architekturstil für Web-APIs. Seine Hauptideen sind:

- Dinge, die die API verwaltet, sind **Ressourcen**, jeweils durch eine URL wie `/customers/42` bezeichnet.
- Die HTTP-Methoden drücken die Operation aus: GET liest, POST legt an, PUT ersetzt, PATCH ändert einen Teil einer Ressource, DELETE entfernt.
- Jede Anfrage ist **zustandslos**: Sie enthält alles, was der Server braucht, er führt also keine Unterhaltung über mehrere Anfragen hinweg.
- Ressourcen werden meist in JSON dargestellt.

Viele APIs, die REST genannt werden, folgen nur einem Teil dieser Ideen. Lies deshalb immer die Dokumentation der konkreten API.

## Authentifizierung und Autorisierung

**Authentifizierung** beantwortet, wer du bist; **Autorisierung** beantwortet, was du tun darfst. Übliche Wege für Zugangsdaten sind ein API-Schlüssel oder ein Token in einem Anfrage-Header. OAuth ist ein Standard, mit dem Nutzende einer Anwendung begrenzten Zugriff auf ihre Daten erlauben, ohne ihr Passwort herauszugeben. Nutze immer HTTPS, schreibe Geheimnisse nie in den Code oder in eine URL, die protokolliert werden kann, und lege sie in Konfiguration oder einem Geheimnisspeicher ab. Status 401 bedeutet meist fehlende oder ungültige Zugangsdaten, 403 bedeutet, dass du bekannt bist, aber nicht darfst.

## Fehler und Robustheit

- Prüfe den Statuscode, bevor du den Body liest, und behandle die 4xx-Familie anders als 5xx: Ein 400 oder 404 wird durch Wiederholen nicht besser, ein 503 kann vorübergehen.
- Setze ein **Timeout**. Ein Aufruf ohne Timeout kann dein Programm ewig blockieren.
- Rechne damit, dass der Body fehlt oder ungültig ist, und behandle Parse-Fehler.
- Logge Anfragekennung und Status fehlgeschlagener Aufrufe, ohne Geheimnisse.
- Bei langen Listen liefern APIs **Seiten**; folge den Seiteninformationen bis zum Ende, statt anzunehmen, dass die erste Antwort vollständig ist.

## Dokumentation und Versionierung

Lies die API-Dokumentation zu Endpunkten, Parametern, Beispielantworten und Fehlerformaten. Eine API ändert sich mit der Zeit, deshalb tragen Anbietende oft eine Version in der URL oder in einem Header. Lege die Version fest, gegen die du getestet hast, und lies Hinweise zu Änderungen und auslaufenden Funktionen.

## Beispiel zur Veranschaulichung

Nur zur Veranschaulichung; erfundener Dienst. Dein Code lädt alle offenen Rechnungen aus einer Abrechnungs-API. Der erste Aufruf liefert 50 Einträge und einen Link zur nächsten Seite; du folgst den Links, bis keiner mehr kommt. Ein Aufruf scheitert mit 401, weil ein Token abgelaufen ist, also fordert dein Client einmal ein neues Token an und wiederholt die Anfrage. Ein anderer Aufruf liefert 503, daher wartet er kurz und versucht es einige Male mit wachsenden Wartezeiten erneut, protokolliert dann den Fehler und meldet ihn, statt abzustürzen. Basisadresse und Token kommen aus der Konfiguration, nicht aus dem Code.

## Wichtige Erkenntnisse

- REST-artige APIs stellen Ressourcen unter URLs bereit und nutzen HTTP-Methoden und JSON.
- Authentifizierung ist, wer du bist, Autorisierung, was du darfst; schütze Geheimnisse und nutze HTTPS.
- Prüfe Statuscodes, setze Timeouts, behandle Seitenwechsel und wiederhole nur Fehler, die vorübergehen können.
- Lies die Dokumentation und lege die getestete API-Version fest.
